# UI Design

## Preserve content and structure

For style-only work, preserve the approved content structure and design tokens.
Use the actual data contract.
Show honest empty states and distinguish errors from empty results.
Inspect the actual render and exercise the key interactions before delivery.

## Give content a clear hierarchy

Do not add cards, tables, sidebars, or decorative states only to fill empty space.
Use content hierarchy, natural spacing, and necessary separators to organize the page.
Do not put a border around every sub-block.

Give each fact or data string one display owner within the same view.
Do not repeat the same fact in adjacent cards, property areas, and status areas.
Remove labels that only explain an obvious control and add no necessary business information.
Do not repeat default states that the context already establishes.
Use status badges for meaningful distinctions, not decoration.

## Use color for meaning

Assign consistent accent-color meanings to actions, changes, and states that need distinction.
Do not use multiple saturated colors for ordinary backgrounds, established facts, or decoration.
Keep specific color values and fixed proportions in the project's design system.

## Separate labels from values

In record and field displays, render static labels and dynamic values separately.
Give them a clear visual hierarchy.
Do not combine them into one display string.
Keep status markers separate from business identifiers.
Use static guidance in search placeholders.
Do not insert dynamic business data into a placeholder.

## Make requested alternatives distinct

When the user requests visual alternatives, keep them within the approved content and structure.
Create substantive differences through typography, hierarchy, surface treatment, or other relevant design choices.
Do not reuse one cluttered template with small background-color changes as multiple alternatives.
